## 1. What we are building

A high-performance Rust trading bot for Polymarket short-duration crypto Up/Down markets:

- **Universe (initial):** BTC and ETH × 5-minute, 15-minute, 1-hour Up/Down series (6 series). The dashboard's per-series comparison later narrows to the best 2–3.
- **Two modes, one engine:** Paper and Live. Paper consumes **real live Polymarket data** — real books, trades, resolutions, fee math — only the money is simulated (operator-adjustable starting capital). The strategy engine is 100% identical between modes; only the execution venue adapter differs.
- **24/7 autonomy:** when a window resolves, the bot rolls to the next window of that series automatically, forever.
- **Strategy (full spec §8):** model-based two-sided quoting (market making) around a fair value from the underlying price feeds, with cancel-first repricing, inventory-skewed quotes, strict pair-cost discipline, and a fee-aware taker module for momentum/late-window opportunities. The core failure mode we engineer against is adverse selection: resting quotes picked off by faster traders when the underlying moves.
- **Dashboard:** served by the bot, showing both paper and live sessions, per-series comparison, live window view, fills, risk state, and controls (incl. paper capital adjustment).
- **Deployment:** Linux VPS close to Polymarket infra (region chosen via our latency benchmark). Development on the operator's PC — §3 build rules are mandatory.

The operator writes no code; you (Claude Code) implement everything, one focused prompt at a time from BUILD_PLAN.md.

## 5. Runtime topology (one process)

Long-running tasks: rtds feed, binance feed, one clob feed per active window pair, scheduler, model (per asset), engine (per series), venue adapter, journal writer, analytics ticker, dashboard server, control plane. The scheduler announces window lifecycle events; engines attach to windows; the risk manager sits between every engine and the venue — **no order reaches a venue without passing risk checks**. Graceful shutdown: stop strategies → cancel all open orders → flush journal → exit.

## 6. Trading universe & 24/7 rollover

- Series: BTC-5m, BTC-15m, BTC-1h, ETH-5m, ETH-15m, ETH-1h. Each independently enable/disable-able at runtime (dashboard + config). All six run concurrently in paper for the evaluation phase.
- Windows are pre-created by Polymarket on a fixed schedule. Discovery must always hold the current active window + ≥1 next window per series, fetched ≥60 s before the current one ends.
- The market WebSocket (custom feature flag, §7) emits `new_market` and `market_resolved` — primary rollover triggers, with wall clock + discovery refresh as fallback so a missed event can never stall a series.
- Per-series lifecycle: Discovering → Pending (subscribed, waiting for open) → Active (trading) → Closing (final-seconds §8) → Resolved (settle, merge/redeem, attribute PnL) → roll. A series with no discoverable next window logs loudly, retries with backoff, never crashes the process.
- Resolution: outcome is Up if the resolution-source end price is **≥** the start price ("price to beat"). Ties resolve Up. Source for 5m/15m = **Chainlink BTC/USD (resp. ETH/USD) data stream**; confirm the 1h series' rules via the API at discovery and store the resolution source per market rather than assuming.

## 7. Polymarket API facts (verified June 2026 — re-verify via docs when implementing)

**Hosts**
- CLOB REST: https://clob.polymarket.com
- Discovery (Gamma): https://gamma-api.polymarket.com (docs "Fetching Markets")
- Market WebSocket: wss://ws-subscriptions-clob.polymarket.com/ws/market
- User WebSocket (auth): wss://ws-subscriptions-clob.polymarket.com/ws/user
- Real-Time Data Socket (RTDS): wss://ws-live-data.polymarket.com
- Docs index: https://docs.polymarket.com/llms.txt

**Official Rust SDK — use it.** Docs show first-class Rust examples (polymarket-client-sdk-v2): order builders (limit + market), separate sign and post, batch posting, automatic fetch of tick size / neg-risk / fee rate inside the builder. Locate via docs Client Reference + crates.io; pin the version. Don't hand-roll EIP-712 signing or auth headers unless the SDK is missing something — if so, document why.

**Auth & wallets.** New API users → **deposit wallets** (docs "Deposit Wallets"; signature types: EOA=0, proxy=1, Gnosis Safe=2, deposit wallet=3). Live trading needs one-time token approvals for the exchange contracts (docs "Trading Quickstart" + "Deposit Wallets"). Collateral/balance denomination: read docs "Polymarket USD (PUSD)" during wallet/ledger work.

**Order types & behaviors**
- GTC, GTD (limit, rest on book) and FOK, FAK (marketable, execute immediately).
- **Post-only** (GTC/GTD): order rejected instead of matching if it would cross. Maker quotes use post-only so we never pay taker fees.
- GTD has a 60-second security threshold: for an effective lifetime of N s, set expiration = now + 60 + N.
- Marketable: BUY = dollar amount, SELL = share count; the price field is a worst-price slippage limit, not a target.
- Batch endpoint: up to 15 orders/request.
- Cancels: by order id, by market (cancel-market), and cancel-all (docs "Cancel Orders"). Wire cancel-all into every safety path.

**Market channel (public)** — subscribe with JSON: token ids under `assets_ids`, `type`="market", `custom_feature_enabled`=true (unlocks best_bid_ask, new_market, market_resolved). Client sends text `PING` ≥ every 10 s (we send 5 s); server replies `PONG`. A text frame is ONE event object OR a JSON ARRAY of them (arrays seen on multi-token subscribe). Events tagged by `event_type`:
- book — full snapshot on subscribe and whenever a trade affects the book; arrays of {price, size} for bids/asks; has asset_id, market (condition id), timestamp, hash (opaque). **Trades reach books ONLY through these snapshots** (~1.2/s per token on an active BTC-5m pair); price_change never carries trade effects.
- price_change — order placed/cancelled; list of per-asset changes with price, size (new TOTAL at that level), side, current best_bid/best_ask; size "0" = level removed. One order is MIRRORED as two entries (BUY Up @ p ↔ SELL Down @ 1−p, same size). **A trade at the touch arrives as a crossing change** (a bid AT the best ask) carrying post-trade tops — the consumed opposite level's removal is never sent as a delta; resolve locally by implied consumption (drop opposite levels at-or-better than the new price), confirmed by the next snapshot (naive crossed-book-recycle loops on every such trade).
- tick_size_change — fired when price crosses 0.96/0.04 and tick flips between 0.01 and 0.001; book and quoting must handle live. (Fixture synthesized from docs — not yet captured live.)
- last_trade_price — trade prints (paper fill sim + markouts); can arrive after the trade's book snapshot (ordering not guaranteed).
- best_bid_ask, new_market, market_resolved — via the custom flag. new_market is a PLATFORM-WIDE broadcast (every new market, any category — dedup + treat as refresh hint). market_resolved arrives on connections subscribed to that market's tokens; condition id in `market` (no condition_id/slug field despite docs), winner in `winning_asset_id`. A closed window's connection must linger ~20–60 s after close to receive it.
- Load: one active 5m pair ≈ up to ~800 msg/s peak; 12 tokens on one connection floods ~1500 msg/s and the server RSTs it — one connection per window pair (§5).

**User channel (auth)** — /ws/user; API credentials inside the subscription message; streams your order updates and trades filtered by API key. Read the full docs page for auth fields/event schemas; reconcile with REST open-orders on every reconnect.

**RTDS (no auth, critical)** — send PING every 5 s; subscriptions are JSON {action subscribe/unsubscribe, list of {topic, type, filters}}; messages arrive as {topic, type, timestamp, payload}.
- Topic crypto_prices = **Binance source**; symbols lowercase concat (btcusdt, ethusdt). Topic crypto_prices_chainlink = **Chainlink source — the resolution feed**; symbols slash format (btc/usd, eth/usd); subscribe with type "*".
- **One filter slot per (connection, topic), replace-not-add** (regression probes `crates/feed-rtds/tests/live_probe.rs`): a later filtered subscribe replaces the earlier filter; no multi-symbol filter form works (comma lists and JSON arrays acked then silent, incl. the docs' comma-list). Multi-symbol = the all-symbols form (crypto_prices: omit `filters`; chainlink: `"filters":""` with type "*"), ~1 update/s/symbol (~13 msg/s total), filtered client-side.
- A **filtered** subscribe (JSON-encoded-string filter `"{\"symbol\":\"btcusdt\"}"` — the only form honored) triggers a ~2-min **backfill** (`payload {symbol, data:[{timestamp, value}…]}`, type "subscribe"); all-symbols form does not. Chainlink backfills arrive under the WRONG topic (crypto_prices) — resolve stream identity from the symbol, never the topic.
- Live updates carry `full_accuracy_value` (lossless string: Binance plain decimal, Chainlink 18-dp fixed-point integer = value×10¹⁸) and `connection_id`. Subscribe ack = empty text frame; no text "PONG" from RTDS. Server can answer a subscribe with an error frame `{body:{message}, statusCode:500}` — observed leaving a symbol's stream dead a whole session; feed-rtds self-heals by recycling the connection when a tracked stream starves.
- Subscriptions can be modified without reconnecting.
- Chainlink offers a sponsored direct Data Streams API key for 15-minute-market traders (request form on the RTDS docs page) — operator to apply later; design feed-rtds so a direct Chainlink source slots in.

**Fees (exact, docs "Fees")**
- fee = shares × feeRate × p × (1 − p), charged to **takers only**, in dollars, at match time by the protocol (nothing in orders). Makers pay zero.
- **Crypto feeRate = 0.07, maker rebate share = 20%.** Per 100 shares: $1.75 @ 0.50, $1.31 @ 0.25/0.75, $0.63 @ 0.10/0.90, $0.07 @ 0.01/0.99. Symmetric around 0.50.
- Fees rounded to 5 decimals; minimum charged 0.00001.
- Per-market fee params are queryable (SDK market-info returns a fee descriptor with rate/exponent/taker-only) and feesEnabled is on the market object — **always read fee params per market at discovery; never hardcode 0.07** in logic (only as a config default).
- Maker Rebates Program: 20% (crypto) of collected taker fees, redistributed **daily in USDC**, proportional to executed maker volume, $1 min accrual (docs "Maker Rebates Program"). A tiered **Taker Rebate Program** exists (docs "Taker Rebates") — fold into taker edge math if material. A **Liquidity Rewards** program exists for resting two-sided quotes — optional income, read during the quoting task.

**Order size & price constraints (operator-confirmed + enforce defensively)**
- Minimum resting order: **5 shares AND $1 notional** — min shares = max(5, ceil_to_size_precision(1.00 / price)), re-validate after tick rounding. At 0.10, $1 binds (10 sh); at 0.50, 5 sh bind ($2.50). Also read minimum_order_size and minimum_tick_size from the market object; take the strictest. Every outgoing order passes the normalizer (§engine) — a rejected-for-size order in production is a bug.
- Tick sizes: 0.1 / 0.01 / 0.001 / 0.0001; our markets 0.01 flipping to 0.001 past 0.96/0.04. Prices land on the current tick grid; valid range [tick, 1 − tick].

**Other pages to read when relevant:** "Matching Engine Restarts" (assume orders may be gone, reconcile + re-quote), "CTF: Merge"/"CTF: Redeem" (matched Up+Down pairs merge to $1 collateral — our capital recycling; redeem after resolution), "Gasless Transactions" (relayer for on-chain ops), "Resolution", "Order Lifecycle", "Resources → Contracts", "Resources → Error Codes" (map error codes to typed errors), "Builders" (optional order attribution).

## 8. Strategy specification (the engine's brain)

**Fair value.** For window strike K (the "price to beat" captured at window start from the resolution-grade feed), current price S, τ seconds remaining: z = ln(S/K) / (σ_1s × √τ), p_up = Φ(z) (standard normal CDF; drift negligible at these horizons; apply the ≥-ties-go-Up rule as a tiny adjustment only if measurement shows it matters). σ_1s is an EWMA of 1-second log returns (half-life default 60 s) with a floor and cap. Chainlink (via RTDS) is ground truth; direct Binance is the fast signal, corrected by a continuously-estimated Chainlink-minus-Binance basis. The model exposes a health state; when inputs are stale/diverging it declares UNRELIABLE and the engine pulls quotes.

**Quoting.** Desired quotes = pure function of (model state, inventory, fee params, config, τ, tick): center = p_up − γ × normalized inventory imbalance; half-spread = max(configured min edge, k1 × σ_1s × √(expected holding time) + a latency premium from the measured cancel round-trip). Two-sided, post-only, small size at the touch with a ladder behind. Gates: no quoting while model UNRELIABLE; widen on vol spikes; **no at-the-money quoting in the final 20–30 s; no passive orders at all in the final ~5 s (cancel-all)**; respect per-window inventory caps.

**Cancel-first repricing.** On any signal tick that moves p_up against a resting quote beyond threshold θ, cancel first (cancel-market on large moves), then re-quote. This is the primary defense against the adverse-selection failure mode — treat its latency as a first-class metric.

**Inventory & pair discipline.** Track per window: shares and cost per side, matched pairs = min(Q_up, Q_down), pair cost = avg_up + avg_down, signed excess, worst-case-if-excess-loses dollars. Only add to a side passively if post-trade pair cost stays ≤ the configured threshold (default 0.98). Soft cap on excess → quote only the deficit-reducing side; hard cap → stop making, optionally work excess off at/above fair. Merge matched pairs back to collateral (live: CTF merge via relayer; paper: simulated instantly-credited merge) to recycle capital across windows.

**Taker modules (fee-aware).** (a) Momentum/staleness: when a confirmed signal-feed move implies the book is stale, take with FAK only if model-vs-book edge exceeds fee(p) + configured buffer (at p≈0.5 the crypto fee ≈1.75¢/share, so mid-window takes need real edge). (b) Late-window: when τ is below a threshold and p_up is beyond a certainty threshold on the Chainlink-anchored price, buy the near-certain side up to a price cap, sized against displayed depth (fees near zero there). Per-window taker budgets and cooldowns apply. Risk manager can veto everything.

**Per-window risk bound.** The configured max worst-case loss per window is the binding constraint on all sizing.

## 9. Paper trading specification

- Same engine, risk manager, order normalizer; only the venue adapter differs.
- **Fill simulation (conservative by design):** a passive paper order is queued behind ALL displayed size at its level at placement (pessimistic queue position); fills only as real last_trade_price prints occur at or through its price, after a simulated placement latency; cancels take effect after a simulated cancel round-trip. Marketable paper orders walk the real displayed book after the simulated latency with partial fills per available depth. Latencies are configurable distributions (defaults: operator-measured RTTs from the latency harness). Paper must never be more optimistic than reality in any code path — when in doubt, fill less.
- **Money:** paper wallet starting capital from config, adjustable at runtime from the dashboard (changes journaled). Taker fees charged using live per-market fee params and the exact formula. Maker rebates accrued as an estimate (rebate share × fee formula on filled maker volume), credited on a simulated daily cycle, reported separately from trading PnL.
- **Settlement:** positions settle on the real market_resolved outcome. Simulated merge converts matched pairs to cash instantly on engine request.
- Paper and live ledgers share one schema; every event is journaled identically so analytics and dashboard treat both modes uniformly.

## 11. Risk rules (hard-wired)

All order flow passes through the risk manager. Non-negotiable: cancel-all on market-WS or user-WS disconnect, on any feed staleness beyond 500 ms, on detected matching-engine restart, and on clock-skew alarm. Per-window max loss; daily stop-loss halting all trading until manual reset; global max open notional; stand-down (pull quotes) whenever |model fair − book mid| exceeds a sanity bound for more than a few seconds; error-rate circuit breaker on API failures; manual kill from dashboard and CLI. **Live arming:** live orders are possible only when config enables live mode AND a specific env var contains a required confirmation phrase AND the operator has armed live mode in the dashboard for the session; absent any one, the live adapter must refuse to construct.

## 14. Glossary

Window = one tradable interval (e.g., BTC Up/Down 11:55–12:00). Series = the repeating product (BTC-5m). Strike / price-to-beat = resolution-source price at window start. Pair cost = combined average cost of one Up + one Down share. Excess = unmatched shares on one side. Markout = signed fair-value move a short interval after a fill; persistently negative markouts on passive fills = we are being adversely selected. Edge = model fair minus executable price, after fees. Merge = converting matched pairs back into $1 collateral. Armed = live trading explicitly enabled per §11.

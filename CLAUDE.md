## 1. What we are building

A high-performance Rust trading bot for Polymarket's short-duration crypto Up/Down markets, with:

- **Universe (initial):** BTC and ETH × 5-minute, 15-minute, and 1-hour Up/Down series (6 series total). The dashboard's per-series comparison will later be used by the operator to narrow down to the best-performing 2–3 series.
- **Two modes, one engine:** Paper and Live. Paper mode consumes **real live Polymarket market data** — real books, real trades, real resolutions, real fee math — only the money is simulated, with operator-adjustable starting capital. The strategy engine must be 100% identical between modes; only the execution venue adapter differs.
- **24/7 autonomy:** when a window resolves, the bot automatically rolls to the next window of that series, forever, with no human action.
- **Strategy (summary, full spec in §8):** model-based two-sided quoting (market making) around a fair value computed from the underlying price feeds, with cancel-first repricing, inventory-skewed quotes, strict pair-cost discipline, and a fee-aware taker module for momentum/late-window opportunities. The core failure mode we are engineering against is adverse selection: resting quotes getting picked off by faster traders when the underlying moves.
- **Dashboard:** served by the bot itself, showing both paper and live sessions, per-series performance comparison, live window view, fills, risk state, and controls (including paper capital adjustment).
- **Deployment target:** Linux VPS located close to Polymarket's infrastructure (operator will choose region using our latency benchmark tool). Development happens on the operator's PC — build performance rules in §3 are mandatory.

The human operator writes no code. You (Claude Code) implement everything. The operator gives you one focused prompt at a time from BUILD_PLAN.md.

3. **Never break the workspace.** Every task ends with the whole workspace compiling, lints clean, and all existing tests passing — not just the crate you touched.
4. **Paper-first, live-gated.** The bot must be incapable of sending a live order unless live mode is explicitly armed (config flag AND environment confirmation AND dashboard arm action, per §11). Default everything to paper. Treat this as a safety invariant, not a feature.
5. **Identical engine paths.** Strategy/engine code must never know which venue it is talking to. If you find yourself writing "if paper / if live" inside engine logic, stop and refactor — mode differences live only in the venue adapters.
6. **Money is decimal, never float.** All prices, sizes, fees, balances use a decimal type (rust_decimal). Floating point is allowed only inside the math model (vol, normal CDF, fair value), and converted at the boundary with explicit rounding rules.
7. **Verify against live reality.** Where the docs are ambiguous (exact market slugs, strike/price-to-beat source, field presence), write a small read-only probe against the live public API, inspect actual responses, then implement and record what you learned in the Decisions Log.
8. **Update this file.** When you make an architectural decision, learn an API fact, or change a parameter default, append it to the Decisions Log (§15) in the same task.

## 3. Build performance (mandatory — the operator's previous Rust project made his PC unusable)

You must configure the project so that day-to-day iteration is fast and the machine stays responsive. Implement all of the following at scaffold time and never regress them:

- **Many small workspace crates** (see §4). Rust recompiles at crate granularity; small crates = small rebuilds. Engine logic must not live in one giant crate.
- **Dev profile:** workspace members compile unoptimized; **all external dependencies compile at optimization level 2 via a profile package override** so they are compiled once, cached, and fast at runtime even in dev. Reduce debug info to line-tables-only in dev to shrink link times.
- **Fast linker:** configure the mold linker on Linux (fallback: lld) through the cargo configuration. Document the one-time system install step in the README.
- **Cap parallelism:** set the default build jobs to (logical cores − 2) via cargo configuration so builds never starve the operator's desktop. Document how to override for the VPS.
- **Iteration workflow:** developers (you) iterate with cargo check / clippy via a watcher (bacon), not full builds. Full release builds happen only for deployment. Encode these as just recipes.
- **Dependency discipline:** TLS is rustls everywhere — never openssl. Keep the dependency tree minimal. Allowlist (add others only with written justification in the Decisions Log): tokio, tokio-tungstenite, serde + serde_json, reqwest (rustls feature), rust_decimal, thiserror, anyhow, tracing + tracing-subscriber, axum + tower, rusqlite or sqlx-sqlite, figment or config, chrono or time, the official Polymarket Rust SDK and only what it transitively requires. Forbidden in the bot workspace: polars, full ethers, openssl-sys, any ORM, any heavyweight GUI toolkit.
- **Feature-gate heavy optional parts** (e.g., replay analytics) so the core bot builds lean.
- A fresh contributor following the README must get a working check loop in under 10 minutes.

## 5. Runtime topology (one process)

Long-running tasks: rtds feed, binance feed, one clob feed per active window pair, scheduler, model (per asset), engine (per series), venue adapter, journal writer, analytics ticker, dashboard server, control plane. The scheduler announces window lifecycle events; engines attach to windows; the risk manager sits between every engine and the venue — **no order reaches a venue without passing risk checks**. Graceful shutdown order: stop strategies → cancel all open orders → flush journal → exit.

## 6. Trading universe & 24/7 rollover

- Series: BTC-5m, BTC-15m, BTC-1h, ETH-5m, ETH-15m, ETH-1h. Each series is independently enable/disable-able at runtime (dashboard + config). All six run concurrently in paper for the evaluation phase.
- Windows are pre-created by Polymarket on a fixed schedule. Discovery must always hold: current active window + at least the next window per series, fetched ≥60 seconds before the current one ends.
- The market WebSocket (with the custom feature flag enabled, §7) emits `new_market` and `market_resolved` events — use these as the primary rollover triggers, with the wall clock + discovery refresh as the fallback so a missed event can never stall a series.
- Per-series lifecycle: Discovering → Pending (subscribed, waiting for open) → Active (trading) → Closing (final-seconds behavior per §8) → Resolved (settle, merge/redeem, attribute PnL) → roll to next. A series with no discoverable next window logs loudly, retries with backoff, and never crashes the process.
- Resolution rule for these markets: outcome is Up if the resolution-source end price is **greater than or equal to** the start price ("price to beat"). Ties resolve Up. Resolution source for the 5m/15m crypto series is the **Chainlink BTC/USD (resp. ETH/USD) data stream** — confirm the 1h series' rules text via the API at discovery time and store the resolution source per market rather than assuming.

## 7. Polymarket API facts (verified June 2026 — re-verify via docs when implementing)

**Hosts**
- CLOB REST: https://clob.polymarket.com
- Discovery (Gamma): https://gamma-api.polymarket.com — see docs page "Fetching Markets" for current endpoints/params
- Market WebSocket: wss://ws-subscriptions-clob.polymarket.com/ws/market
- User WebSocket (authenticated): wss://ws-subscriptions-clob.polymarket.com/ws/user
- Real-Time Data Socket (RTDS): wss://ws-live-data.polymarket.com
- Docs index for discovery: https://docs.polymarket.com/llms.txt

**Official Rust SDK exists — use it.** The docs show first-class Rust examples under the name polymarket-client-sdk-v2: order builders (limit and market), separate sign and post steps, batch posting, automatic fetch of tick size / neg-risk / fee rate inside the builder. Locate the crate via the docs Client Reference pages and crates.io; pin the version. Do not hand-roll EIP-712 signing or auth headers unless the SDK is missing something — if it is, document why in the Decisions Log.

**Auth & wallets.** New API users are directed to **deposit wallets** (see docs "Deposit Wallets"; signature types include EOA = 0, proxy = 1, Gnosis Safe = 2, deposit wallet = 3). Live trading also requires one-time token approvals for the exchange contracts — follow the docs "Trading Quickstart" + "Deposit Wallets" exactly. Collateral/balance denomination: read docs "Polymarket USD (PUSD)" concept page during wallet/ledger work and follow it.

**Order types & behaviors**
- GTC, GTD (limit, rest on book) and FOK, FAK (marketable, execute immediately).
- **Post-only** flag exists for GTC/GTD: the order is rejected instead of matching if it would cross. Our maker quotes should use post-only so we never accidentally pay taker fees.
- GTD has a 60-second security threshold: for an effective lifetime of N seconds, set expiration = now + 60 + N.
- Marketable orders: BUY is specified as a dollar amount, SELL as a share count; the price field on them is a worst-price slippage limit, not a target.
- Batch endpoint: up to 15 orders per request.
- Cancels: by order id, by market (cancel-market), and cancel-all. Read docs "Cancel Orders" for exact endpoints. Wire cancel-all into every safety path.

**Market channel (public)** — subscribe with a JSON message containing the list of token ids under assets_ids, type set to "market", and custom_feature_enabled set to true (this unlocks best_bid_ask, new_market, and market_resolved events). Client must send the text `PING` at least every 10 s (we send every 5 s); the server replies `PONG`. A text frame carries either ONE event object or a JSON ARRAY of them (arrays observed live on the multi-token subscribe delivery). Event types, each tagged by an event_type field:
- book — full snapshot on subscribe and whenever a trade affects the book; arrays of {price, size} for bids and asks; includes asset_id, market (condition id), timestamp, hash (opaque — algorithm undocumented). **Trades reach the books ONLY through these snapshots** (~1.2/s per token observed on an active BTC-5m pair); price_change never carries trade effects.
- price_change — order placed/cancelled; carries a list of per-asset changes each with price, size (the new TOTAL at that level), side, and current best_bid / best_ask; a size of "0" means that level was removed. One order appears MIRRORED as two entries (BUY Up at p ↔ SELL Down at 1−p, same size). **A trade at the touch arrives as a crossing change** (a bid AT the best ask) carrying the post-trade tops — the consumed opposite level's removal is never sent as a delta; resolve locally by implied consumption (drop opposite levels at-or-better than the new price), confirmed by the next snapshot (verified live 2026-06-12; naive crossed-book-recycle looped on every such trade).
- tick_size_change — fired when price crosses 0.96 / 0.04 and tick flips between 0.01 and 0.001. The book and our quoting must handle this live. (Not yet captured live — fixture synthesized from docs.)
- last_trade_price — trade prints (used by the paper fill simulator and markouts); can arrive after the trade's book snapshot (ordering not guaranteed).
- best_bid_ask, new_market, market_resolved — via the custom feature flag. new_market is a PLATFORM-WIDE broadcast (every new market on the venue, any category — dedup + treat as refresh hint only). market_resolved arrives on connections subscribed to that market's tokens; its condition id is in `market` (no condition_id/slug field despite the docs' field list), winner in `winning_asset_id`. A closed window's connection must linger to receive it (~20–60 s after close observed).
- Load shape: one active 5m token pair ≈ up to ~800 msg/s peak; 12 tokens on one connection floods ~1500 msg/s and the server RSTs it — one connection per window pair (§5).

**User channel (authenticated)** — same host, /ws/user path; API credentials go inside the subscription message; streams your order updates and trades filtered by API key. Read the full docs page for exact auth fields and event schemas before implementing; reconcile with REST open-orders on every reconnect.

**RTDS (no auth, critical for us)** — send PING every 5 seconds; subscriptions are JSON messages with action subscribe/unsubscribe and a list of {topic, type, filters}; messages arrive as {topic, type, timestamp, payload}.
- Topic crypto_prices = **Binance source**; symbols lowercase concatenated (btcusdt, ethusdt). Topic crypto_prices_chainlink = **Chainlink source — this is the resolution feed for these markets**; symbols slash format (btc/usd, eth/usd); subscribes with type "*".
- **One filter slot per (connection, topic), replace-not-add** (verified live 2026-06-12; regression probes in `crates/feed-rtds/tests/live_probe.rs`): a later filtered subscribe on a topic replaces the earlier filter, and no multi-symbol filter form works (comma lists and JSON arrays are acked then silent — including the docs' plain comma-list form). Multi-symbol streaming = the all-symbols form (crypto_prices: omit `filters`; chainlink: `"filters":""` with type "*"), ~1 update/s per symbol (~13 msg/s for everything), filtered client-side.
- A **filtered** subscribe (JSON-encoded-string filter `"{\"symbol\":\"btcusdt\"}"` — the only filter form the server honors) triggers a ~2-minute **backfill** message (`payload {symbol, data:[{timestamp, value}…]}`, type "subscribe"); the all-symbols form does not. Chainlink backfills arrive under the WRONG topic (crypto_prices) — stream identity must be resolved from the symbol, never the topic.
- Live updates additionally carry `full_accuracy_value` (lossless string: Binance plain decimal, Chainlink 18-dp fixed-point integer = value×10¹⁸) and `connection_id`. The subscribe ack is an empty text frame; no text "PONG" reply was observed from RTDS. The server can answer a subscribe with an error frame `{body:{message}, statusCode:500}` — observed live, left one symbol's stream dead for an entire session; feed-rtds self-heals by recycling the connection when a tracked stream starves.
- Subscriptions can be modified without reconnecting.
- Note: Chainlink offers a sponsored direct Data Streams API key for 15-minute-market traders via a request form linked on the RTDS docs page — worth the operator applying later; design feed-rtds so a direct Chainlink source could be slotted in.

**Fees (exact, from docs "Fees")**
- Formula: fee = shares × feeRate × p × (1 − p), charged to **takers only**, in dollars, at match time by the protocol (nothing to include in orders). Makers pay zero.
- **Crypto category feeRate = 0.07, maker rebate share = 20%.** Reference points per 100 shares: $1.75 at p=0.50, $1.31 at 0.25/0.75, $0.63 at 0.10/0.90, $0.07 at 0.01/0.99. Symmetric around 0.50.
- Fees rounded to 5 decimals; minimum charged fee 0.00001.
- Per-market fee params are queryable (the SDK exposes a market-info call returning a fee descriptor with rate/exponent/taker-only fields) and feesEnabled is on the market object — **always read fee params per market at discovery; never hardcode 0.07** in logic (hardcode only as a config default).
- Maker Rebates Program: 20% (crypto) of collected taker fees redistributed **daily in USDC**, proportional to your executed maker volume, $1 minimum accrual — read docs "Maker Rebates Program" for the precise accrual definition when implementing the rebate estimator. A separate tiered **Taker Rebate Program** exists (docs "Taker Rebates") — read and incorporate into taker edge math if material. A separate **Liquidity Rewards** program also exists for resting two-sided quotes — optional income, read its page during the quoting-engine task.

**Order size & price constraints (operator-confirmed + enforce defensively)**
- Minimum resting order: **5 shares AND $1 notional** — i.e., minimum shares = max(5, ceil_to_size_precision(1.00 / price)), then re-validate after tick rounding. At 0.10, $1 binds (10 shares); at 0.50, 5 shares bind ($2.50). Also read minimum_order_size and minimum_tick_size from the market object and take the strictest constraint. Every outgoing order passes the normalizer (§ engine) — a rejected-for-size order in production is a bug.
- Tick sizes possible: 0.1 / 0.01 / 0.001 / 0.0001; our markets are 0.01 flipping to 0.001 past 0.96/0.04. Prices must always land on the current tick grid; valid range is [tick, 1 − tick].

**Other pages that must be read when relevant:** "Matching Engine Restarts" (handle restarts: assume orders may be gone, reconcile + re-quote), "CTF: Merge" and "CTF: Redeem" (matched Up+Down pairs merge back to $1 of collateral — our capital-recycling mechanic; redemption after resolution), "Gasless Transactions" (relayer for those on-chain ops), "Resolution", "Order Lifecycle", "Resources → Contracts" and "Resources → Error Codes" (map API error codes to typed errors), "Builders" (optional order attribution).

## 8. Strategy specification (the engine's brain)

**Fair value.** For a window with strike K (the "price to beat" captured at window start from the resolution-grade feed), current price S, and τ seconds remaining: z = ln(S/K) / (σ_1s × √τ), and p_up = Φ(z) (standard normal CDF; drift is negligible at these horizons; apply the ≥-ties-go-Up rule as a tiny adjustment only if measurement shows it matters). σ_1s is an EWMA of 1-second log returns (configurable half-life, default 60s) with a floor and cap. Chainlink (via RTDS) is ground truth; direct Binance is the fast signal, corrected by a continuously-estimated Chainlink-minus-Binance basis. The model exposes a health state; when inputs are stale/diverging it declares UNRELIABLE and the engine pulls quotes.

**Quoting.** Desired quotes are computed as a pure function of (model state, inventory, fee params, config, τ, tick): center = p_up − γ × normalized inventory imbalance; half-spread = max(configured minimum edge, k1 × σ_1s × √(expected holding time) + a latency premium derived from our measured cancel round-trip). Two-sided, post-only, small size at the touch with a ladder behind. Gates: no quoting while model UNRELIABLE; widen on vol spikes; **no at-the-money quoting in the final 20–30s; no passive orders at all in the final ~5s (cancel-all)**; respect per-window inventory caps.

**Cancel-first repricing.** On any signal tick that moves p_up against a resting quote beyond a threshold θ, cancel first (cancel-market on large moves), then re-quote. This single behavior is the primary defense against the adverse-selection failure mode (resting quotes being picked off by faster traders the instant the underlying moves) — treat its latency as a first-class metric.

**Inventory & pair discipline.** Track per window: shares and cost per side, matched pairs = min(Q_up, Q_down), pair cost = avg_up + avg_down, signed excess, and worst-case-if-excess-loses dollars. Only add to a side passively if the post-trade pair cost stays ≤ the configured threshold (default 0.98). Soft cap on excess → quote only the deficit-reducing side; hard cap → stop making, optionally work excess off at/above fair. Merge matched pairs back to collateral (live: CTF merge via relayer; paper: simulated instantly-credited merge) to recycle capital across windows.

**Taker modules (fee-aware).** (a) Momentum/staleness: when a confirmed signal-feed move implies the Polymarket book is stale, take with FAK only if model-vs-book edge exceeds fee(p) + configured buffer — at p≈0.5 the crypto fee is ≈1.75¢/share, so mid-window takes need real edge. (b) Late-window: when τ is below a threshold and p_up is beyond a certainty threshold on the Chainlink-anchored price, buy the near-certain side up to a price cap, sized against displayed depth (fees are near zero out there). Per-window taker budgets and cooldowns apply. Risk manager can veto everything.

**Per-window risk bound.** The configured maximum worst-case loss per window is the binding constraint on all sizing.

## 9. Paper trading specification

- Same engine, same risk manager, same order normalizer; only the venue adapter differs.
- **Fill simulation (conservative by design):** a passive paper order is queued behind ALL displayed size at its level at placement time (pessimistic queue position); it fills only as real last_trade_price prints occur at or through its price, after a simulated placement latency; cancels take effect after a simulated cancel round-trip. Marketable paper orders walk the real displayed book after the simulated latency with partial fills per available depth. Latencies are configurable distributions (defaults: operator-measured RTTs from the latency harness). It must be impossible for paper to be more optimistic than reality in any code path — when in doubt, fill less.
- **Money:** paper wallet starting capital comes from config and is adjustable at runtime from the dashboard (changes are journaled). Taker fees are charged using the live per-market fee params and the exact formula. Maker rebates are accrued as an estimate (rebate share × fee formula applied to our filled maker volume) and credited on a simulated daily cycle, reported separately from trading PnL.
- **Settlement:** positions settle on the real market_resolved outcome. Simulated merge converts matched pairs to cash instantly when the engine requests it.
- Paper and live ledgers share one schema; every event is journaled identically so analytics and dashboard treat both modes uniformly.

## 11. Risk rules (hard-wired)

All order flow passes through the risk manager. Non-negotiable behaviors: cancel-all on market-WS or user-WS disconnect, on any feed staleness beyond 500 ms, on detected matching-engine restart, and on clock-skew alarm. Per-window maximum loss; daily stop-loss that halts all trading until manual reset; global maximum open notional; stand-down (pull quotes) whenever |model fair − book mid| exceeds a sanity bound for more than a few seconds; error-rate circuit breaker on API failures; manual kill from dashboard and CLI. **Live arming:** live orders are only possible when the config enables live mode AND a specific environment variable contains a required confirmation phrase AND the operator has armed live mode in the dashboard for the session; absent any one of these, the live adapter must refuse to construct.

## 14. Glossary

Window = one tradable interval (e.g., BTC Up/Down 11:55–12:00). Series = the repeating product (BTC-5m). Strike / price-to-beat = resolution-source price at window start. Pair cost = combined average cost of one Up + one Down share. Excess = unmatched shares on one side. Markout = signed fair-value move a short interval after a fill; persistently negative markouts on passive fills = we are being adversely selected. Edge = model fair minus executable price, after fees. Merge = converting matched pairs back into $1 collateral. Armed = live trading explicitly enabled per §11.
